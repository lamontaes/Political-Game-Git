# File a pool item by hand

Part of the `pool-notes` skill. Until Nov 17, 2026 this was the `file-a-pool-item` skill; the CTO merged it here when the skills were capped (owner: "Let's go ahead"). What it covered: Adds or changes a pool item by hand, without npm run pool -- add: the file under docs/pool/items, the Cause prefixes the standard allows, the release declaration. Use whenever you find something worth an item while working, and before writing an item's Cause. Not for claiming or finishing an item (session-start) or pool-only bundles (pool-notes).

`npm run pool -- add`, `claim` and `next` push to main. On this account nothing pushes to main, so edit the item file yourself, on the thread's own branch.

- **Search first** (`look-first`): `docs/pool/items` for a match. If one exists, add your evidence to its Notes instead of a twin.
- Copy a neighboring item's frontmatter: `id`, `lead`, `standard: 2`, `model`, `effort`, time box, `Files`, `Waits on`. The id is the file name.
- **Cause begins with one of four prefixes** and nothing else (`.agents/rules/pool-item-standard.md`):
  - `Found in code:` a path that exists, with a function or line, and the record ids followed.
  - `Measured:` the place and seed, or the command that shows it.
  - `Design:` the owner's ruling or the design page it follows.
  - `Needs cause.` an item that is not built until someone finds it (`docs/pool/FIND-A-CAUSE.md`).
- **Fix** names the existing function it changes and says where the player sees it; an item with no place the player sees is dropped. **Done when** keeps the words "second session".
- Do not set `checked:`; the lead does.
- Add a release declaration `docs/release/changes/<id>.md`. `impact: none` has no section or title; any title is under 140 characters.
- Run `npm run pool -- --check 2>&1 | grep <item-id>` (its tail shows only the last lines) and clear every line for your item before pushing, or CI's pool guard fails; also run prettier on the file. A "What" is three sentences and 40 words, a "Done when" names a drawn place ("in a drawn place, Town, State (seed ...)") and a second session, and a "Rules" line names a standing rule with six words after it. Known reds on two words items are not yours. What the check refuses (Nov 15): sections out of the order What, Cause, Fix, Time box, Rules, Done when, Waits on, Files (Notes last); a What whose last sentence does not begin `Seen:` (a quote at the very end can hide it, so end on plain words); a `Measured:` with no place and seed or command; a Done when that does not say "second session" and "drawn place"; a `Design:` naming a docs path that does not exist; `status: in-pr` with an empty `pr:`; a Rules section that does not name one of `STANDING_RULES` (scripts/pool/index.ts, such as "Ask why:") with at least six words after it. Locally the pool guard checks only items your branch changes against main, so on a branch built on the train read your own items against these rules before pushing; CI checks against the train and catches it after the push.
- A declaration with `impact: patch` (a player-facing fix) needs `section: Fixed` and a `title:`, and `release:check` reads the committed file, so commit before rerunning it.
- The item goes in the thread's own PR, not a PR of its own.
- An item you set `status: in-pr` needs `pr:` filled, and the PR number exists only after the PR is opened: open the draft, then set `pr: <number>` in a second commit (the pool guard reads 19 of 20 until you do; Nov 15, the town hall stop).
- **Write an item with every field named, never positionally (Nov 15).** A shell function that filled the template by argument position shifted each field down one (the Cause text landed under What, the file list under Waits on) and CI's pool guard failed on all three items; the local check had not looked at them yet. Write the file with named fields, then open it, run `npm run pool -- --check` and read what it says of your items.
- **The check reads a `Needs cause.` item word for word (Nov 15, views thread).** Its Fix is exactly `None until the cause is found.` and nothing more; a likely fix goes in a Notes line. Its What has at least three sentences and 40 words, and its last sentence begins `Seen:`, `Feeds: <item id>` or `Guards:`.
- **What the checker enforces on a hand-written item (Nov 15).** Sections come in this order: What, Cause, Fix, Time box, Rules, Done when, Waits on, Files, Notes. `area` is one of the listed areas (a press fix is `director`). The last sentence of What begins `Seen:`, `Feeds: <item id>` or `Guards:` and sits on its own line (a sentence that follows a closing quote on the same line is not found). A "Found in code:" cause names an existing path and a line number or function. Done when says what a second session sees and names a drawn place. `status: open` until the PR has a number.
- **What the pool check refuses** (Nov 15, filing `metrics-paper-looking-for-work-line-pinned`): the What paragraph must end with a sentence that begins `Seen:`, `Feeds: <item id>` or `Guards:`, and Done when must name a drawn place. A `Measured:` Cause must contain the word "seed" (`REALISTIC_SEED=` alone does not count). Run the pool check right after filing. A `pr:` is required once the status is `in-pr`, so name the PR number the moment the PR exists and rerun the gate on that head.
- **A Measured cause names the place, the seed and the command in its first sentence (Nov 15).** The pool check reads `Measured: at <place>, seed <x>, by \`<command>\`, ...`and refuses a Cause that begins with the prefix but puts the place and command after it in parentheses. An`after:`or`blocked-on:` names an item that exists on the branch you file on, so leave both empty for an item whose neighbor is still in an open PR and name it under Waits on.
- **`kind` is one of bug, feature, wiring, stopgap, research, cleanup or owner-decision (Nov 17).** The check refuses any other word (`gap` was refused); a missing mechanic is a feature. The Time box names a number of hours, and the Rules line names one of `STANDING_RULES` in `scripts/pool/index.ts` by its exact words ("Research before building", "No dice", "No hand-written player text"), not a rule's skill name; "Simulate it, don't ask" is not on that list.
- **`root:` is `none` or a name listed in `docs/pool/roots.md` (Nov 15).** A stopgap id is not a root; the check refuses it. A Rules section names a standing rule (`no-dice`, `wire-to-the-world`) with six or more words saying how it applies.
- **A Notes bullet appended after the Notes paragraph needs a blank line before it (Nov 17).** Two items written by script (`words-run-family-filing-lines-are-composed` on the hour's bundle, `words-press-comment-rewritten-with-inserts` on #9794) failed the repository job's prettier check for a `- 2026-11-17 ...` line glued to the paragraph above. Run `npx prettier --write` on the item before committing, in a helper copy or on the file you send through the contents API.
- **Fields the pool guard also wants on every hand-written item (Nov 16, world thread).** An `after:` line (empty is fine) sits between `blocked-on:` and `lead:`, and an item at `status: in-pr` needs `pr: <number>` in a second commit once the PR exists. A kept table the item adds needs its row in `docs/design/daily-register.md` (`speed-work` (cadence-and-summaries part)), or the `guards` job fails on `tests/guards/daily-register.test.ts`. Run `npm run pool -- --check` and `npx vitest run tests/guards/daily-register.test.ts` before the first push.
