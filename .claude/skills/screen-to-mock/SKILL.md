# Screens follow the mock, through shared parts

**Look first:** run the `look-first` search before building, fixing, filing or asking; a found ruling is built and cited, never asked again.

The standard is `docs/play-first/LAW.md` section 1: menu screens follow the look the owner locked on Nov 5 (dark see-through textured panel, no boxes, glowing hover, lit selection, portraits in light, data not sliders or bar graphs, no checkboxes); the CTO holds the clickable mock, and no menu is built until the owner approves its screen. The Oct 14 mocks are deleted. The approved set is `docs/mocks/2026-11-07-approved/`, with the menu rulings of Nov 5 to 8 numbered in its `RULINGS-nov5.md`; the owner conditionally approved every mock so far on Nov 8 and wants the same principles applied to every other screen, so a screen with no mock of its own follows the look and rulings of the set rather than waiting. Owner, Oct 26: "I've given a billion UI samples. Why the hell is this still a jumbled mess?" and "There's a bunch of independent UI things... This all needs to be unified... there's too much duplication."

## Rules

- Name the LAW.md section 1 line the change serves in the PR body, and the owner's approval of that menu's screen. No approved screen, no menu: the CTO holds the clickable mock and finds the ruling first.
- Put the approved screen and the after screenshot side by side in the PR body (1440×900, drawn place and seed).
- One shared component per control (panel, card, list row, menu, toast, talk box, tab, button). Reuse it; never write a second renderer for the same control. If the shared part doesn't exist yet, make it its own module and move the existing copies onto it in the same PR (Replace, never layer).
- Cards where the approved screen has cards, never text rows. A list of people shows face, office and party, and every person is clickable to their card everywhere they appear.
- Many choices open a real menu or panel, never a long numbered list in the talk box (owner, Oct 26).
- One way to each screen: no rail icon and menu line that both open the same thing unless the approved screen shows both.
- Nothing on screen does nothing: a control with no effect, a toast with no way to close, an empty panel or heading is a defect.
- Panels fit the window and use their space: no large empty areas, no see-through text panels over busy art.
- **A screen PR lands in its stack's merge order, then merges main and sets the kit baseline from the guard.** Sibling screen PRs all edit `src/bench/play.mjs` and `tests/guards/kit-only-ui-baseline.json`, and mergers never hand-merge UI code, so each one that lands first sends the rest back. Merge main, keep both sides of `play.mjs`, run `tests/guards/kit-only-ui.test.ts`, set the baseline to the count the guard reports (it only shrinks), and rerun the screen's browser check in a drawn place (Oct 28: #6557, #6563, #6564 and #6594 each sent back for this one conflict in a two-hour window).
- **Browser checks write their screenshots into `docs/`** (`docs/reports/...`, `docs/play-first/shots/...`); after running one, `git checkout -- docs/reports docs/play-first/shots` before committing, so a check's draw never replaces another PR's evidence (Oct 29: the politics check rewrote #6832's shots twice).
- **A screen redesign updates the browser checks that read it in the same PR**, by running every `*.browser.mjs` that names the screen's old classes (`grep -l` the old selector); several were already stale on main after #6832 (card-history, politics-people, party, guide-menu) and only showed up when the next screen PR ran them.
- **Sizes, corners, colors and type are named once.** `src/bench/ui/README.md` is the UI system's page: names in `:root` of `src/bench/play.css` (the type scale `--t-label` to `--t-display`, `--control-h`, `--control-pad`, `--control-radius`, `--control-font`, `--pick-*`, `--head-*`), one part per control in `src/bench/ui/`, and screens that only call parts. A rule never types its own pixel size, corner or hex color; `tests/guards/ui-tokens.test.ts` counts the ones still typed by hand and the count may only go down. A list a player picks from beside its page is `pickHead`, `pickGroup` and `pickRow` from `ui/list-row.mjs`. (Owner, Nov 10: "Make sure that the UI system is unified so that when it's time to adjust the UI in the future... it's way easier to change stuff on a screen or on a menu.")
- **A person on a menu is a bust.** `src/bench/bust.ts` picks the pieces from the person's record and puts them on the face record (`face.bust`); `src/bench/ui/bust.mjs` is the only part that draws one, through `bust()` in `strips.mjs` and `headshot()`. No screen crops a face from a full-body figure, and no whole figure stands beside a menu (owner, Nov 7 and Nov 10). The art and the painter's spec: `art/busts/v1/` and `docs/art/busts-spec.md`.
- **Merger:** a screen change without the owner's approved screen, or with a second renderer for an existing control, is a send-back.
- **A screen that changes how a control reads, pages or numbers breaks the checks that find it by name (Fixer 2, Nov 8).** (1) A number drawn by CSS (`content: counter(choice) "."`) joins the button's accessible name, so a check that finds "Go vote" by exact name no longer does; write `content: counter(choice) "." / ""` so it stays out of the name (screen readers too). (2) A list that pages hides later entries from a check until it turns the page; `src/bench/trail-act.mjs` shows how a check turns pages until its tile shows, and a check that waits for a tile that is not drawn fails after its own timer, not with a locator error. (3) A screen that opens its first row by default makes a check that "clicks the first row and waits for a change" wait forever; click another row. (4) Before blaming a screen for a timed-out check, read what is on screen when it stalls (a screenshot every few passes of its loop): this night the stalls were a conversation waiting for a reply, a second morning for a household member, a polling place holding the clock and a player with no money, all the check's own.
- **No arrows and no "1 of N" on lists or pages (owner, Nov 8: "like those shitty survey sites"; Nov 9: "Lists only").** A stepper that changes one value (dev Run's days, the creator's color rows, world settings) keeps its arrows. The one long-list box (`ui/pager.mjs`) is a bounded box that scrolls inside itself; a long list that has a detail (patch notes, the journal's chapters) sits beside it, and the detail scrolls in its own box (`.patch-detail`). Never add arrows, a page counter or a "next page" control. A browser check that needs a row far down the list clicks it (Playwright scrolls it into view); it never turns pages.
- **Staging waits for busts (owner, Nov 10).** Do not file or reopen full-body staging defects (who stands where, people blocking each other in a room) while busts are coming; how busts are shown is the owner's call.
- **The bench serves `controls.json` from memory (Nov 8, Screens).** After editing `src/bench/data/controls.json`, restart `npm run bench` before a browser check, or the screen draws with the old words and fails on a missing key. Browser checks also rewrite tracked screenshots in `docs/reports` and the repository root: `git checkout --` them, and delete untracked ones, before `git add -A`.
- **A page taller than its sheet scrolls inside its columns, never as a page (Nov 11, the bill page).** The pattern: `#sheet-body:has(<the screen>) { display: flex; flex-direction: column; overflow: hidden }`, the screen `flex: 1; min-height: 0`, its column grid `grid-template-rows: minmax(0, 1fr)`, and each column `min-height: 0; overflow-y: auto`. What a player must act on (a vote, a button) goes in the first column, never under the grid.
- **A list beside a page that redraws itself uses `rosterScreen`'s `show`.** `render(entry, show)` may return the page's nodes, or call `show(...nodes)` now and again after each action (a bill after a vote), so the page stays beside its list. A row carries its entry's key as `data-key`; a check opens a row by that, never by its place in the list.
- **A bust is a stack of pictures, so a check counts `.bust-stack`, never `img` (Nov 11).** `person-card.browser.mjs` expected one image in the card's bust and found four.
- **"Before" pictures need main's code running, on the same seed (Nov 11, the strip).** Commit, check out `origin/main` in the same checkout, restart the bench, start the life with `POST /api/newlife?seed=<the seed>`, picture it, then go back to your branch and restart the bench again. A fresh draw on each side shows two different rooms and proves nothing. Stop every check that is running against the bench before you switch.
- **A check that starts from a saved life inherits what the last check did to it (Nov 11).** `person-card.browser.mjs` continued a life in which an earlier script had already used up everyone's talk, and timed out waiting for someone to click. Start a fresh life first, or run it before anything that talks.
- **A check that clicks a row in a list beside a page waits for that row's page (Nov 11, the merge desk's send-back on the Bills list).** The page that was on screen before the click stays there while the new one loads, so a check that reads the page at once reads the wrong entry (three of five draws read the wrong bill and found no chair). `rosterScreen` marks its page with the entry it shows: wait for `.roster-page[data-key="<the entry's key>"]`, then read.
- **A stack that is squash-merged is gone from your branch's history.** After the top of a stack merges, start the follow-up from main and cherry-pick your new commits; merging main into the old branch conflicts with your own work (Nov 11, #8511).

## Lesson of Nov 11 (a list beside a page left dead buttons)

The list-beside-page part (`rosterScreen`) hands a page a `show` to redraw itself with. Clicking the row of the entry already open started a second draw and stopped listening to the first, whose buttons were still on screen. A vote cast there reached the game and never the page.

- **A list does not open the entry that is already open.**
- **A page that redraws itself shows only its newest draw.** Two acts close together each redraw; the earlier one can finish its reads last.
- **Check it:** in the page's browser check, click the open entry's own row, act on the page, and read the result on the page.
